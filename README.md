# NetPilot

Прокси-менеджер с веб-интерфейсом: узлы, подписки, группы и правила «Кто → Что → Куда».
Ядро подключаемое: sing-box встроен, Xray, mihomo и Hiddify ставятся кнопкой.

## Сборка (Windows)

```powershell
.\build.ps1                 # dist\netpilot.exe
.\build.ps1 -Targets all    # + Linux amd64 / arm64 / armv7 / mipsle
.\build.ps1 -Run            # собрать и запустить
.\build.ps1 -Targets linux -Compress   # сжать Linux-сборки UPX (для роутеров)
```

Go ставить не нужно: если его нет, скрипт скачает официальный портативный Go в `.tools\go`.

## Запуск

**Windows:** `dist\netpilot.exe`, затем откройте http://127.0.0.1:2017.
Настройки хранятся в папке `data` рядом с местом запуска (или `-data <путь>`).

**Docker:**

```powershell
docker compose up -d --build
```

Интерфейс: http://localhost:2017, прокси: `localhost:7890` (HTTP и SOCKS5).
Пароль интерфейса задаётся через `NETPILOT_PASSWORD` в `docker-compose.yml` (логин `admin`).

**Linux (служба systemd):** пример службы — `deploy/netpilot.service`, установка
бинарника — `deploy/install-binary.sh`.

Параметры запуска: `-listen` / `NETPILOT_LISTEN` (адрес интерфейса),
`-data` / `NETPILOT_DATA`, `-password` / `NETPILOT_PASSWORD`,
`NETPILOT_PROXY_LISTEN` (адрес прокси при первом запуске),
`NETPILOT_ALLOWED_HOSTS` (дополнительные имена интерфейса, см. ниже).

## Первая настройка и доступ

Если пароль не задан через `NETPILOT_PASSWORD`, его придумывают при первом входе
(логин `admin`):

- с этого же компьютера (адрес 127.0.0.1) — сразу;
- с другого устройства — нужен одноразовый код первой настройки. Он печатается в журнал
  программы при каждом запуске, пока пароль не задан:

  ```
  docker compose logs netpilot      # Docker
  journalctl -u netpilot            # служба systemd
  ```

  На Windows код виден в окне консоли программы. В Docker с пробросом портов запрос
  приходит в контейнер не с 127.0.0.1, поэтому код нужен и с той же машины.

Без кода пароль успел бы задать любой в сети, кто первым откроет страницу. После
нескольких неверных кодов подряд ввод с этого адреса временно блокируется.

Забыли пароль — остановите NetPilot, удалите файл `auth.json` в папке данных
(`/var/lib/netpilot` у службы systemd, `data` рядом с программой на Windows) и запустите
программу снова: в журнале появится новый код первой настройки. Остальные настройки
не пострадают.

Интерфейс отвечает, только если в адресной строке IP-адрес, `localhost`, имя этой
машины, однословное имя (`zimaos`) или имя в локальной зоне (`.local`, `.lan`, `.home`,
`.home.arpa`, `.internal`, `.localdomain`). Остальные имена отклоняются — это защита
от DNS rebinding (чужой сайт направляет своё имя на адрес NetPilot). `NETPILOT_ALLOWED_HOSTS`
нужен, если интерфейс открывают по другому имени: своя запись в локальном DNS
(`netpilot.home`) или обратный прокси (nginx, Caddy). Список через запятую:
`NETPILOT_ALLOWED_HOSTS=netpilot.home,np.lan`; `*` выключает проверку.

## Режимы работы

**Прокси-сервер** — устройства указывают адрес прокси (HTTP и SOCKS5 на порту 7890).
Работает везде: Windows, Linux, Docker. На Windows NetPilot может включить системный
прокси для программ этого компьютера (Настройки → Режим работы); если программа
завершилась аварийно, оставшийся системный прокси убирается при следующем запуске.

**Прозрачный шлюз** — NetPilot сам перехватывает трафик устройств, для которых он шлюз:
на устройствах ничего настраивать не нужно. Только Linux (nftables + TPROXY):

```bash
docker compose -f docker-compose.gateway.yml up -d --build
```

Как устроен перехват:

- устройства с маршрутом «Напрямую» и локальные адреса проходят мимо ядра прокси —
  решение принимается в ядре Linux, без задержки;
- «Без интернета» отбрасывается там же, локальная сеть остаётся доступной;
- DNS-запросы устройств перехватываются (отключается в настройках);
- IPv6 по умолчанию блокируется (устройства сразу переходят на IPv4), его можно
  перехватывать так же, как IPv4, или не трогать;
- трафик самого сервера и контейнеров Docker не трогается;
- при остановке ядра перехват снимается, а если программа завершилась аварийно,
  остатки правил удаляются при следующем запуске — сеть устройств не «зависает».

Проверка на настоящем ядре Linux (стенд «клиент → шлюз → интернет»):

```powershell
docker compose -f test/transparent/docker-compose.yml up -d --build
powershell -File test/transparent/run.ps1
```

## Ядра

| Ядро | Как работает | Особенности |
|---|---|---|
| sing-box | встроено | все протоколы кроме XHTTP, статистика соединений |
| Xray | ставится кнопкой | XHTTP; без статистики соединений |
| mihomo | ставится кнопкой | Hysteria2, TUIC, статистика соединений |
| Hiddify | ставится кнопкой | sing-box с дополнениями Hiddify, тот же конфиг: Hysteria2, TUIC, статистика соединений; без XHTTP |

Xray, mihomo и Hiddify скачиваются с GitHub разработчиков в `data/cores/`. Каждый файл
сверяется с контрольной суммой: у Xray — с файлом `.dgst` из релиза, у mihomo и Hiddify —
с SHA256, которую GitHub публикует для каждого файла релиза. Без проверки ядро
не ставится. Hiddify есть для Windows amd64 и Linux amd64 / arm64 / armv7 / mipsle.

В режиме «Авто» выбирается ядро, которое поддерживает все узлы;
узлы, которые выбранное ядро не поддерживает, исключаются из его конфигурации и
показываются в интерфейсе. Ядро завершается вместе с NetPilot, даже при аварийном
завершении (Job Object на Windows, PDEATHSIG на Linux). Журналы ядер ограничены
по размеру (4 МБ плюс одна старая копия), чтобы не занять флеш-память роутера.

### Если ядро упало

Если внешнее ядро (Xray, mihomo, Hiddify) неожиданно завершилось, NetPilot запускает его
снова с нарастающей паузой (2 с, 5 с, 15 с, 30 с, минута). После 5 сбоев за 10 минут
перезапуск прекращается: в интерфейсе появляется ошибка, ядро нужно запустить вручную,
посмотрев его журнал.

Что происходит с устройствами в прозрачном режиме, пока ядра нет, задаёт настройка
«Если ядро упало» (Настройки → Режим работы):

- **Пускать напрямую** (по умолчанию) — перехват снимается, устройства идут в интернет
  без прокси;
- **Блокировать интернет** (kill switch) — перехват остаётся, интернета нет, пока ядро
  не вернётся.

В режиме роутера так же перезапускаются упавшие dnsmasq, udhcpc и pppd.

Процесс ядра может работать, а трафик — нет (например, повисло соединение с DNS-сервером).
Поэтому раз в 20 секунд NetPilot спрашивает у ядра случайное имя тем же путём, что и
устройства. Если ядро трижды подряд не ответило, а у самого сервера интернет есть,
NetPilot переключает прямой DNS на следующий сервер (при «auto») или перезапускает ядро,
как после падения.

Пока ядро не работает (упало, зависло или остановлено в панели), запросы устройств к DNS
шлюза пересылаются на DNS самой системы (роутера или провайдера). Иначе после снятия
перехвата трафик шёл бы напрямую, но сайты всё равно не открывались бы: DNS у устройств
указан на шлюз. В режиме роутера это не нужно — DNS там отвечает dnsmasq NetPilot.

### DNS

Прямой DNS по умолчанию — `auto`: Cloudflare (1.1.1.1), Google (8.8.8.8), Quad9 (9.9.9.9),
Яндекс (77.88.8.8) — последним запасным. NetPilot берёт первый отвечающий (DoH),
переключается на следующий, если текущий перестал отвечать, и раз в 30 минут пробует
вернуться к более приоритетному. Свой сервер (`https://…`, `tls://…`, IP или `local`)
можно указать в Настройки → DNS.

## Трафик и соединения

Скорость и объём по устройствам и список активных соединений берутся из Clash API ядра
(sing-box, mihomo, Hiddify). Из списка соединений можно одним нажатием создать правило
«всегда напрямую» или «всегда через прокси» для сайта. Учитывается трафик, проходящий
через NetPilot.

## Подписки

Для каждой подписки задаётся интервал автообновления. Если узлы изменились и других
неприменённых изменений нет, конфигурация применяется автоматически. Если сайт
провайдера недоступен напрямую, подписка загружается через работающий прокси.

## Настройки и резервные копии

Настройки хранятся в `data/config.json` вместе с номером версии формата (`schema`).
Файл от старой версии программы обновляется при запуске, прежний сохраняется рядом
как `config.json.bak`. Файл от более новой версии программа не трогает и не запускается,
а пишет, что нужно обновить программу или восстановить резервную копию.

Резервная копия перед восстановлением проверяется целиком (формат, версия, все узлы,
группы, правила, устройства и подписки); если в ней ошибки, текущие настройки не меняются.

## Обновление программы

NetPilot сам проверяет новые версии в GitHub Releases, ставит — по кнопке «Обновить».
Список файлов релиза (`SHA256SUMS`) подписан ключом ed25519, открытый ключ встроен
в программу при сборке: релиз, подписанный другим ключом, не установится, даже если
сменить репозиторий. Новая версия пробно запускается, предыдущая сохраняется: если новая
несколько раз подряд не проработала и минуты, возвращается прежняя. Смена источника
обновлений (репозиторий или токен) подтверждается текущим паролем.

Сборка без `release.pub` в корне репозитория подпись не проверяет — интерфейс об этом
предупреждает. Как выпустить релиз: [docs/RELEASING.md](docs/RELEASING.md).

## Устройства в сети

NetPilot сам находит устройства: опрашивает подсеть, читает таблицу ARP и узнаёт имена
(DHCP-аренды OpenWrt, обратный DNS, NetBIOS), а производителя — по MAC (реестр IEEE,
встроен в программу; обновление: go run internal/oui/gen/main.go). Устройства узнаются по MAC, поэтому правила
продолжают работать, если незакреплённое устройство получило новый IP.

Для каждого устройства задаётся маршрут всего трафика — «По правилам», «Через прокси»,
«Напрямую» или «Без интернета» — и закрепление IP. На OpenWrt закреплённые адреса
записываются в DHCP (dnsmasq) автоматически; в остальных случаях их нужно зарезервировать
и на роутере.

Где работает сканирование:

| Запуск | Видит локальную сеть |
|---|---|
| `netpilot.exe` на Windows | да |
| OpenWrt | да, плюс управление DHCP |
| Docker на Linux (ZimaOS) с `network_mode: host` | да |
| Docker Desktop на Windows/macOS | нет — контейнер работает в виртуальной машине |

Отключить слежение за сетью: `-scan=false` или `NETPILOT_SCAN=0`.
Разработка интерфейса без пересборки: `NETPILOT_WEB_DIR=web\static`.

## Безопасность

- У прокси (порт 7890) нет авторизации: им пользуется любой, кто до него достучится.
  Не открывайте его в интернет. Docker публикует порты на всех интерфейсах в обход
  файрвола хоста (ufw/firewalld их не закрывают) — если машина доступна из интернета,
  замените в `docker-compose.yml` `"7890:7890"` на `"127.0.0.1:7890:7890"` или адрес
  в локальной сети (см. комментарий там). С `docker-compose.gateway.yml` (сеть хоста)
  закройте порт файрволом хоста.
- Интерфейс работает по обычному HTTP и рассчитан на локальную сеть. Не открывайте
  порт 2017 в интернет; для доступа извне — VPN или обратный прокси с HTTPS
  (его имя добавьте в `NETPILOT_ALLOWED_HOSTS`).
- Задайте `NETPILOT_PASSWORD` или сразу пройдите первую настройку с кодом из журнала,
  пока этого не сделал кто-то другой.

## Устройство

```
cmd/netpilot          точка входа
internal/model        единая модель конфигурации (не зависит от ядра), проверка, миграции формата
internal/core         интерфейс ядра, реестр, автовыбор по возможностям
internal/core/singbox адаптер sing-box: модель → конфиг, запуск внутри процесса
internal/core/xray    адаптер Xray (отдельный процесс)
internal/core/mihomo  адаптер mihomo (отдельный процесс)
internal/core/hiddify адаптер Hiddify Core (отдельный процесс, конфиг sing-box)
internal/core/external запуск внешних ядер, установка с GitHub с проверкой сумм
internal/core/logfile журналы ядер с ограничением размера
internal/firewall     прозрачный режим: nftables + TPROXY
internal/router       режим роутера: PPPoE/DHCP/статический IP, NAT, раздача адресов
internal/sysproxy     системный прокси Windows: уборка после аварийного завершения
internal/oui          производители по MAC
internal/scan         обнаружение устройств: ARP, NetBIOS, шлюз
internal/dhcp         закрепление IP (статические аренды dnsmasq на OpenWrt)
internal/links        разбор ссылок vless/vmess/trojan/ss/hysteria2/tuic и подписок
internal/profiles     профили приложений (домены и IP сервисов)
internal/store        хранение в data/config.json (атомарная запись, версия формата)
internal/auth         пароль, сессии, код первой настройки
internal/update       самообновление: проверка подписи, откат
internal/app          управление ядром, слежение за падением, проверка задержки, подписки
internal/api          REST API
web/static            веб-интерфейс (без сборщиков, встраивается в бинарник)
web-m3                интерфейс Material 3 Expressive (Compose Multiplatform, Gradle)
tools/releasekey      ключ подписи релизов: создание, подпись, проверка
```

Оформлений интерфейса два: классическое (`web/static`) и Material 3 Expressive
(Настройки → Оформление). Material 3 — отдельное приложение в `web-m3`: оно собирается
Gradle (нужен JDK 17+) в `web/static/m3` и встраивается в бинарник вместе с остальным
интерфейсом. `release.ps1` пересобирает его сам (`-SkipM3` — взять готовый из
`web/static/m3`); вручную: `web-m3\gradlew.bat -p web-m3 publishM3`.

Как правила превращаются в маршрутизацию без лишних задержек:

- доменные условия проверяются до DNS, поэтому совпавший домен уходит сразу;
- DNS-запрос (`resolve`) делается только перед первым правилом по IP/стране;
- списки geosite/geoip скачиваются напрямую, поэтому нерабочий узел не мешает запуску;
- локальная сеть всегда идёт напрямую (отключается в правилах).

## Тесты

```powershell
.\.tools\go\bin\go.exe test -tags with_quic,with_utls,with_clash_api ./...
```

Тест `internal/core/singbox` прогоняет сгенерированный конфиг через настоящий sing-box
(все протоколы, группы, типы правил), поэтому несовместимость с новой версией ядра видна сразу.

Фаззинг парсера ссылок и подписок (подписки — недоверенный вход):

```powershell
.\.tools\go\bin\go.exe test -tags with_quic,with_utls,with_clash_api -run='^$' -fuzz='^FuzzParse$' -fuzztime=1m ./internal/links
.\.tools\go\bin\go.exe test -tags with_quic,with_utls,with_clash_api -run='^$' -fuzz='^FuzzParseMany$' -fuzztime=1m ./internal/links
```

Найденные падения сохраняются в `internal/links/testdata/fuzz` и дальше проверяются
обычным `go test`.

CI (`.github/workflows/ci.yml`) на каждый пуш и pull request: `go vet` (Linux и Windows),
`go test -race`, staticcheck, govulncheck, короткий фаззинг `internal/links` и сборка
под все платформы релиза (Windows amd64, Linux amd64 / arm64 / armv7 / mipsle).
